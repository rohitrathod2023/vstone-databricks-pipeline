Capstone project · Databricks Free Edition

vstone-databricks-pipeline

An end-to-end Bronze → Silver → Gold medallion pipeline built on the xxjcaxx/trafficsimulator Kaggle dataset — simulated traffic sensor data for a neighborhood in Valencia, Spain. Runs entirely on Databricks Free Edition (serverless compute only, no managed clusters), governed by Unity Catalog, deployed via Databricks Asset Bundles (DABs), with a GitHub Actions CI/CD pipeline. Currently: Bronze layer complete (Days 1-3 of a 10-day build), Silver/Gold not yet started.

How this project fits together

Everything is built in layers, where each layer only depends on the layer below it — never the reverse. This is the single most important idea for explaining "how does it all connect."

A trainer question like "why does chunking.py not know what catalog it's writing to?" has one answer that covers the whole project: nothing in Layer 2/3 ever hardcodes an environment-specific value — every path, catalog name, and schema name is resolved at runtime from Layer 0/1, so the exact same code runs unmodified in dev/test/prod.

Foundational files — Config layer

These five files hold every environment-specific and dataset-specific value in the project. Nothing below this layer ever hardcodes a catalog name, schema name, file path, or column type.

configdatabricks.yml

The DABs bundle definition — the single file databricks bundle commands read to know what to deploy and where. Declares 3 targets: dev (mode: development, default), test, prod (both mode: production) — each mapped to its own Unity Catalog catalog via the catalog variable, since Free Edition is a single workspace (no separate dev/test/prod workspaces exist, so catalogs are the closest real separation available).

mode: development is what makes dev's schema names auto-prefix per-user (dev_<user>_raw instead of plain raw) and job names get a [dev <user>] prefix — this is a DABs built-in behavior, not something this project's code does manually.

The include: list is what actually pulls resources/*.yml files into the deploy — a new job/pipeline yml file left out of this glob simply never gets deployed, silently.

configresources/catalog.yml

Declares Unity Catalog schemas and Volumes as DABs-managed infrastructure — deployed the same way as jobs (databricks bundle deploy), not hand-run SQL. Four schemas: raw (landing files), bronze (first Delta tables), audit (pipeline run logs), ops (streaming checkpoints — added later, see the checkpoint-relocation fix below). Two volumes: raw_volume (under raw) and checkpoints_volume (under ops).

Catalog creation itself is deliberately not in here — DABs' declarative catalogs: resource only works with a newer deployment engine this project doesn't use, so the catalog is created once by hand (one-line SQL) per environment.

Why 4 separate schemas, not 1: raw/bronze are data layers, audit is human-queryable pipeline history, ops is opaque pipeline bookkeeping (streaming offsets) — three genuinely different concerns that shouldn't share governance/retention rules.

configsrc/config/env.yml

Per-environment values that aren't per-dataset (that's sources.yml's job). One block per environment (dev/test/prod), each with catalog, raw_schema, bronze_schema, audit_schema, ops_schema.

Why schema names live here instead of being hardcoded "raw"/"bronze" everywhere: mode: development auto-prefixes schema names (dev_<user>_raw) but mode: production doesn't (test/prod stay plain raw) — so the same conceptual schema has a different real name per environment. Every string field here becomes a ${placeholder} usable in sources.yml automatically — adding a new per-environment field needs zero code changes, just a new key here.

configsrc/config/sources.yml

Every ingestable dataset in the project, described once: path, format, technique, target_table, description. Notebooks never hardcode a path — they call get_source_config("<key>") and everything is driven from here. Adding a new source is a config edit, not a code change.

Two kinds of entries:

  • Full entries (raw_cars, chunk1_csv...chunk4_xml) — define their own path/format directly.
  • Indirection entries (bronze_streets, bronze_node_locations, bronze_streets_list, bronze_telegram) — set source_key: raw_streets etc. to reuse another entry's path/format/description, only overriding technique/target_table. This exists because the 4 un-chunked raw files (streets.csv etc.) get ingested into Bronze under a different table name than their raw landing entry — same file, two roles.

has_audit_columns: true on the 4 chunk entries flags that chunking.py already stamped audit columns onto these files at Day 1 extraction time — Bronze's own load has to strip and re-tag them (see copy_into.py below), not collide with them.

configsrc/config/schemas.py

One explicit pyspark.sql.types.StructType per source key, added after Day 3 to replace every inferSchema usage in the project. Every field is deliberately StringType — this isn't an oversight, it's Databricks' own documented medallion-architecture recommendation: Bronze stays loosely typed (string) so an unexpected value in the source file never breaks raw ingestion; strict typing (IntegerType, TimestampType) and schema-equality validation belong to the Silver layer, not built yet.

Column order matters for the 4 CSV schemas (CSV schema application is positional) — every order here was verified directly against the real file headers on the Volume, not just copied from the profiling doc (which, for cars.csv specifically, listed a different order than the actual file uses).

CARS_SCHEMA, STREETS_SCHEMA, NODE_LOCATIONS_SCHEMA, STREETS_LIST_SCHEMA, TELEGRAM_SCHEMA

Five StructTypes. CARS_SCHEMA is reused for all 4 chunks (chunk1_csv..chunk4_xml) plus raw_cars — same 5 source columns (enter,exit,date,id,location) regardless of on-disk format (CSV/JSON/XML). Only node_locations.location and streets_list.street_id are nullable=False — the two genuine primary keys among all 9 sources.

SCHEMAS: Dict[str, StructType]

The lookup table keyed by source_key — consumed by config_loader.get_source_schema(), never imported directly by pipeline code.

Foundational files — src/common/ (shared utilities)

Every pipeline module in Layer 2 imports from here. This is the layer that turns Layer 0's static config into something Python code can actually call.

commonsrc/common/config_loader.py

Loads env.yml and sources.yml, resolves ${placeholder} substitution, and resolves the source_key indirection. This is the one file every other Layer 1/2 module imports from.

Depends on: src/config/env.yml, src/config/sources.yml, src/config/schemas.py (local import inside get_source_schema)
get_env_config(env: str | None = None) -> dict

Returns the active environment's block from env.yml. If env is omitted, falls back to the DATABRICKS_BUNDLE_TARGET env var (set automatically when a job runs via DABs), then "dev".

get_source_config(key: str, env=None) -> dict

The main entrypoint every pipeline calls. Resolves source_key indirection (merges the referenced entry's fields in first, so the alias's own fields win), then substitutes every ${...} placeholder using the active env block. Returns one flat dict — callers never see the indirection or the placeholders.

get_source_schema(source_key: str) -> StructType

Same indirection resolution as get_source_config, but looks up config/schemas.py's SCHEMAS dict instead. Added post-Day-3 alongside schemas.py.

_substitute(value, replacements) -> Any

Generic recursive ${key} replacer — works on strings, dicts, and lists, so any new per-environment field added to env.yml is automatically usable in sources.yml with zero code changes here.

commonsrc/common/io_readers.py

Strategy-pattern dispatch: "read/write this source, regardless of format." A registry (READERS/WRITERS dicts keyed by "csv"/"json"/"xml") means adding Parquet later is one function + one registry entry, nothing else in the repo changes.

read_csv/read_json/read_xml(spark, path, schema=None, **options)

If schema is given, applies .schema(schema). If not, read_csv falls back to inferSchema=true (kept only for hypothetical ad hoc use — every real caller in this project always passes an explicit schema now).

read_source(spark, source_config, schema=None, **options) / write_source(df, source_config, mode="overwrite", **options)

The two functions pipeline code actually calls — look up source_config["format"] in the registry and dispatch. chunking.py is the main caller of both.

commonsrc/common/audit.py

One function, used identically in Bronze/Silver/Gold (Silver/Gold not built yet, but the contract already holds).

add_audit_columns(df, source_format, source_file) -> DataFrame

Adds 4 columns: load_dt (real TimestampType, current_timestamp()), source_format, source_file, run_id (from logger.current_run_id() — ties every row back to the pipeline run that wrote it). These 4 are the only columns in the whole project that are not plain StringType, since they're pipeline-generated metadata, not inferred/typed-from-source data.

commonsrc/common/logger.py

Every module gets its logger the same way: get_logger(__name__, catalog=..., job_name=...). Two things happen per call: (1) a standard Python logger prints to stdout — visible in the Databricks job run UI automatically, and (2) the same event best-effort appends to <catalog>.<audit_schema>.pipeline_logs, a real Delta table backing the "Audit & Observability Layer."

get_logger(name, catalog=None, job_name=..., write_to_delta=True, spark=None)

Idempotent — safe to call repeatedly without duplicating handlers. Attaches a _DeltaAuditHandler when catalog is given.

_DeltaAuditHandler._resolve_table(catalog) -> str

Resolves <catalog>.<audit_schema>.pipeline_logs via config_loader.get_env_config() — not a hardcoded literal "audit". This was a real bug found and fixed post-Day-3: the schema is auto-prefixed under mode: development just like raw/bronze, so a hardcoded name silently failed to write anything in dev the whole time (best-effort design meant it never crashed, just quietly no-op'd).

_DeltaAuditHandler.emit(record)

Never raises — any write failure disables itself for the rest of the run and logs once at DEBUG. Deliberate: a logging call must never be what breaks a pipeline.

current_run_id() -> str

One UUID per process, shared by every logger instance in that run — this is what audit.add_audit_columns tags every row with.

commonsrc/common/metadata.py
apply_table_comments(spark, table, table_comment, column_comments=None)

Config-driven COMMENT ON TABLE/COMMENT ON COLUMN — pulls the comment straight from sources.yml's description field, so there's one place to describe a dataset, not two. Called at the end of every Bronze notebook.

commonsrc/common/sanity_checks.py
run_sanity_check(spark, table, catalog, job_name) -> dict

The brief's "sanity check per ingestion" requirement, as one reusable function. Fails if row_count == 0 or if any present audit column is fully null (catches a silent all-NULL audit stamp, not just an empty load). Every Bronze notebook raises RuntimeError if this fails — which is why "job succeeded" already implies "row_count > 0" without needing a separate count check.

Day 1 — Data Chunking. Splits cars.csv (24.6M rows) into 4 chronological slices, each destined for a different Bronze ingestion technique. This is the only place raw data gets transformed before Bronze.
pipelinesrc/pipelines/ingestion/chunking.py

All real chunking logic — unit-testable without a running job (see test_chunking.py).

Depends on: audit.add_audit_columns, config_loader.get_source_config/get_source_schema, io_readers.read_source/write_source, logger.get_logger/current_run_id
CHUNK_PLAN = [(40,"chunk1_csv"), (30,"chunk2_csv"), (20,"chunk3_json"), (10,"chunk4_xml")]

Chronological, not equal, split — earliest 40% first. Mirrors a real pipeline's growth pattern (one big historical backfill, then progressively smaller incremental drops) and lets each Bronze technique map to the batch size it suits (COPY INTO for bulk, Auto Loader/DLT for smaller incremental, PySpark for the riskiest/smallest write path).

run(spark, env="dev", force=False) -> dict[chunk_key, row_count]

Reads raw_cars with its explicit schema, sorts by date (source row order isn't guaranteed chronological), assigns a monotonic row_number(), and slices by cumulative percentage. Each slice gets audit columns stamped, then written in its target format (chunk1/2 stay CSV, chunk3 becomes JSON, chunk4 becomes XML).

Idempotency, two layers: (1) every write is mode="overwrite" on a fixed path, so a naive re-run replaces rather than duplicates; (2) on top of that, force=False skips the entire expensive sort/write if a completion marker says it's already done — re-deriving just the existing row counts instead of resorting 24.6M rows.

chunking_already_complete(env) / mark_chunking_complete(env)

Checks/writes a _chunking_complete marker file, not bare chunk-file existence — a run that crashed partway through writing would leave a partial file that looks "done" to an existence check, silently leaving bad data in place. The marker is only written after all 4 chunks succeed.

notebooksrc/notebooks/00_download_raw_data.py

Downloads all 5 raw files from Kaggle directly into the Volume — no laptop involved, no 5GB Catalog Explorer upload limit (that cap is a UI restriction, not a Volume storage limit). force=false by default skips files already present. schema is resolved via config_loader.get_env_config(env)["raw_schema"], not a hardcoded widget default.

notebooksrc/notebooks/01_data_chunking.py

Thin entrypoint — reads the catalog/env/force widgets, calls chunking.run(spark, env=env, force=force), prints a sanity-check summary. No real logic lives here.

resourceresources/jobs/data_chunking_job.yml

The "Data Chunking" DABs job — display name kept exactly that literal string (brief requirement) even though it now runs two tasks: download_raw_data → chunk_cars_csv (real depends_on orchestration, added post-Day-3 — see the fix-up section below). No cluster spec on either task = serverless by default, required on Free Edition.

Day 2 — Bronze COPY INTO. Bulk-loads chunk1_csv plus the 4 un-chunked raw files into 5 separate Bronze tables — one table per source, not a shared table (Bronze's grain is one-technique-per-table).
pipelinesrc/pipelines/bronze/copy_into.py

One generic loader reused for all 5 COPY INTO sources — only source_key differs per call.

Depends on: config_loader.get_source_config/get_source_schema, logger.current_run_id
build_create_table_sql(cfg, source_key) -> str

COPY INTO requires its target table to already exist (confirmed against a real warehouse — DELTA_MISSING_DELTA_TABLE_COPY_INTO otherwise). Builds an explicit CREATE TABLE IF NOT EXISTS (col STRING, ..., load_dt TIMESTAMP, ...) from the source's schema — not a CTAS over inferred read_files() (that was the pre-fix version; see the explicit-schemas section).

build_copy_into_sql(cfg, run_id) -> str

The actual COPY INTO ... SELECT ... FROM '<path>' statement. _select_clause() picks * for raw files but * EXCEPT (load_dt, source_format, source_file, run_id) for the 4 chunks — since those already carry audit columns from Day 1's extraction, and a plain SELECT * would collide (COLUMN_ALREADY_EXISTS).

run_copy_into(spark, source_key, env="dev") -> dict

Runs the create-table SQL, then the COPY INTO. COPY INTO tracks which source files it's already loaded internally (in the target table's own transaction log) — re-running against the same file is naturally idempotent, no separate checkpoint needed for this technique.

notebooksrc/notebooks/02_bronze_copy_into.py

One shared notebook, run 5 times by the job below with a different source_key widget each time. Calls run_copy_into, then metadata.apply_table_comments, then sanity_checks.run_sanity_check (raises if it fails).

resourceresources/jobs/bronze_copy_into_job.yml

"Bronze COPY INTO" job — 5 independent tasks (copy_into_chunk1_csv, _streets, _node_locations, _streets_list, _telegram), no depends_on between them since the 5 sources are fully independent — they run in parallel.

Day 3 — Auto Loader, PySpark read/write, and Delta Live Tables. The remaining 3 chunks, one per remaining required ingestion technique.
pipelinesrc/pipelines/bronze/autoloader_ingest.py

Auto Loader (cloudFiles) ingestion for chunk3_json. Structured Streaming under the hood, even though it's used here as a one-shot batch trigger.

Depends on: audit.add_audit_columns, config_loader.get_env_config/get_source_config/get_source_schema
checkpoint_path(cfg, env) / schema_location(cfg, env)

Two separate paths under /Volumes/<catalog>/<ops_schema>/checkpoints_volume/<table>/{checkpoint,schema} — added post-Day-3. Originally these were nested under raw_volume and shared one path; both were fixed (see below).

run_autoloader(spark, source_key, env="dev") -> dict

Loads .load(cfg["path"]) — the exact file path, not the shared chunks/ directory + a glob filter. An earlier attempt used cloudFiles.pathGlobFilter, which got case-folded server-side into an unrecognized option key on this runtime (CF_UNKNOWN_OPTION_KEYS_ERROR); the exact-path approach sidesteps that entirely. Streams with trigger(availableNow=True) (process what's there, then stop — not a long-running stream) into the target table.

Idempotency: the checkpoint's offset log remembers which files were already processed — re-running is naturally a no-op for files already loaded, via a different mechanism than COPY INTO's (streaming checkpoint vs. transaction-log file-tracking).

pipelinesrc/pipelines/bronze/pyspark_xml_ingest.py

Plain PySpark read/write for chunk4_xml — the only Bronze technique with no built-in rerun-safety of its own.

sanitize_column_name(name) -> str

Replaces anything that isn't alphanumeric/underscore with _ — XML tag/attribute names can contain characters (spaces, -, :) that aren't valid Delta/Parquet column names.

run_pyspark_xml(spark, source_key, env="dev") -> dict

Reads via io_readers.read_xml (spark-xml package) with the explicit schema, sanitizes column names, writes with mode="overwrite" — the explicit fix for the missing rerun-safety: the whole file is rewritten wholesale every run, not incrementally, so there's no "new rows since last run" concept a keyed MERGE would need.

pipelinesrc/pipelines/bronze/dlt_traffic_counts.py

Delta Live Tables definition for chunk2_csv. Structurally different from the other 3 — it's a @dlt.table-decorated function, not a plain callable, and runs inside a managed DLT pipeline, not a notebook task directly. Excluded from flake8 individually (setup.cfg) since it uses the same injected-globals pattern (spark) as notebooks despite living under src/pipelines/.

@dlt.table(name="traffic_counts_dlt", comment=...) @dlt.expect(...) def traffic_counts_dlt()

Reads chunk2_csv with its explicit schema, re-tags audit columns, returns the DataFrame — DLT handles the actual materialization. Uses @dlt.expect for data-quality checks (DLT's own native mechanism) rather than sanity_checks.run_sanity_check, deliberately — bolting an imperative check onto a declarative function would fight the framework instead of using its own DQ tooling. Catalog/target schema come from the pipeline resource yml, not this file — DLT tables are declared with their bare name only.

notebooksrc/notebooks/03_bronze_autoloader.py & 04_bronze_pyspark_xml.py

Same thin-entrypoint pattern as 02_bronze_copy_into.py — read widgets, call the Layer 2 function, apply table comments, run the sanity check.

resourceresources/jobs/bronze_autoloader_pyspark_dlt_job.yml + resources/pipelines/bronze_dlt_pipeline.yml

"Bronze Auto Loader / PySpark / DLT Ingestion" job — 3 tasks: autoloader_chunk3_json, pyspark_chunk4_xml (both plain notebook_tasks), and dlt_chunk2_csv (a pipeline_task that triggers the separate DLT pipeline resource by pipeline_id).

The DLT pipeline's target uses ${resources.schemas.bronze_schema.name} — a DABs cross-resource reference, not a literal "bronze" string. This matters because env.yml's bronze_schema field is only visible to Python code via config_loader, never to DABs' own YAML templating — a literal here would silently write DLT's tables into a schema that doesn't exist in dev (since dev's real schema name is prefixed).

Post-Day-3 fix-ups. Three follow-on changes made after the Bronze layer was functionally complete — deliberate design upgrades, not bug fixes for broken code (except the audit-schema one, which was a real latent bug).
fix-upJob orchestration + skip-based idempotency

Before this: the download notebook had to be run manually before data_chunking_job had anything to chunk. After: data_chunking_job.yml gained a download_raw_data task with chunk_cars_csv depending on it — one job, two tasks, the whole Day 1 pipeline runs unattended from nothing.

Also added: chunking.py's force parameter and completion-marker skip-check (see Day 1 section above) — re-running with nothing changed no longer re-sorts 24.6M rows just to rewrite the same output.

bug fixAudit schema resolution

logger.py's _DeltaAuditHandler hardcoded the audit table as <catalog>.audit.pipeline_logs — a literal "audit". Since mode: development auto-prefixes schema names (real dev schema: dev_<user>_audit), every audit log write in dev had been silently failing since Day 1 (best-effort design meant it never crashed anything, just quietly wrote nothing). Fixed by resolving audit_schema through config_loader.get_env_config(), matching how raw_schema/bronze_schema already worked everywhere else. Confirmed fixed live — pipeline_logs now actually has rows.

design upgradeBronze explicit (string-typed) schemas

Every implicit-schema read across the whole Bronze layer — inferSchema in io_readers.py, COPY INTO's inferred CTAS, Auto Loader's un-schema'd .load(), spark-xml's sampling, DLT's inferSchema=true — replaced with one explicit, permissive schema per source (schemas.py). This is Databricks' own documented recommendation, not an invented convention: Bronze stays string-typed on purpose so a bad value never breaks ingestion; strict typing is Silver's job.

A gotcha this surfaced: the 8 Bronze tables already existed with the old inferred types (e.g. enter INT) — CREATE TABLE IF NOT EXISTS is a no-op against an existing table, so all 8 had to be dropped and recreated for the fix to actually take effect. Verified live via DESCRIBE TABLE afterward: every source column is now STRING, audit columns keep their own correct types.

design upgradeAuto Loader checkpoint relocation

The checkpoint originally lived inside raw_volume (the same Volume as the raw landing data) — a conceptual mismatch: a streaming checkpoint is pipeline operational state, not data, and shouldn't live in the same zone whose whole job is holding untouched source files. Fixed by adding a dedicated ops schema + checkpoints_volume (see catalog.yml above), and rewriting checkpoint_path()/schema_location() to point there instead, keyed by target table name.

A second, independent bug found via Databricks' own docs while researching this: checkpointLocation and cloudFiles.schemaLocation were sharing the exact same path — Databricks explicitly documents this as a mistake (you can't clear schema-evolution state without also discarding the checkpoint's exactly-once processing history). Now two separate subpaths.

Relocating the checkpoint makes Auto Loader treat chunk3.json as unprocessed again (fresh checkpoint = fresh stream state), so the target table had to be dropped first to avoid duplicate-appending the same data.

Dependency map — who imports whom

Read top-to-bottom: every arrow means "imports from" / "reads config from." Nothing at the bottom ever imports from the top.

chunking.py → audit, config_loader, io_readers, logger copy_into.py → config_loader, logger autoloader_ingest.py → audit, config_loader pyspark_xml_ingest.py → audit, config_loader, io_readers dlt_traffic_counts.py → audit, config_loader, dlt (external) config_loader.py → schemas.py (local import inside get_source_schema) audit.py → logger.py (current_run_id) logger.py → config_loader.py (local import inside _resolve_table) io_readers.py → (no internal deps -- pure pyspark wrapper) metadata.py → (no internal deps -- pure SQL string builder) sanity_checks.py → logger.py # Notebooks (Layer 3) import from pipelines/ and common/ directly -- never # from each other, and pipelines/ never imports from notebooks/ or resources/.

Notice audit.py → logger.py and logger.py → config_loader.py is a one-way chain, not a cycle — config_loader.py never imports logger.py back. That's what keeps the whole dependency graph a clean DAG instead of a tangle.

Trainer Q&A cheat sheet

If asked...Answer
"Why 4 different ingestion techniques for one file?"The brief requires demonstrating COPY INTO, Auto Loader, DLT, and plain PySpark read/write. cars.csv was chunked chronologically (40/30/20/10) so each technique gets a differently-sized, differently-formatted slice, mapped to the batch size it suits best.
"Why is everything StringType at Bronze?"Deliberate, per Databricks' own medallion guidance — Bronze must never break on an unexpected raw value. Strict typing is Silver's explicit responsibility, not done yet.
"How does a notebook know which catalog/schema to write to?"It never hardcodes one — every notebook reads a catalog/env widget, passes it to config_loader.get_source_config(), which resolves ${catalog}/${raw_schema}/etc. from env.yml's block matching that environment.
"What makes each pipeline idempotent?"A different mechanism per technique: COPY INTO tracks loaded files in the target table's transaction log; Auto Loader tracks them in its streaming checkpoint; plain PySpark uses mode="overwrite" since it has no built-in tracking at all; chunking.py adds a completion-marker skip-check on top of overwrite-safety.
"Why are notebooks so thin?"All real logic lives in src/pipelines/ so it's unit-testable with local PySpark, no Databricks cluster needed. Notebooks only wire job parameters to that logic.
"What's the difference between raw, bronze, audit, and ops schemas?"Four genuinely different concerns: raw = untouched landing files, bronze = first Delta tables, audit = human-queryable pipeline run logs, ops = opaque pipeline bookkeeping (streaming checkpoints) — kept separate so each can have its own governance/retention rules.
"What's left before Day 4?"Silver layer: strict typing + schema-equality validation against those strict types, dedup, the node_locations bad-coordinate quarantine, telegram's inconsistent date parsing — all deliberately deferred, not forgotten.
